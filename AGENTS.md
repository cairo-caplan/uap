# OpenHW Unified RISC-V IP Access Platform (UAP) - Agent Guide

## Project Overview

This repository hosts the Unified RISC-V IP Access Platform (UAP), a static website that serves as a catalog and access point for RISC-V IP assets developed in European research projects such as TRISTAN and ISOLDE. The platform provides:

- IP catalogue with search and filtering capabilities
- Compatibility matrix showing interoperability between components
- Documentation and status information for hardware and software components
- Links to source repositories hosted on OpenHW Foundation GitHub or on third-party websites or repositories
- Editor functionality for creating and modifying IP data files

## Key Directories and Files

### Core Application Files
- `unified-access.html` - Main HTML page implementing the IP catalogue and compatibility matrix
- `script.js` - JavaScript application providing dynamic functionality for the Platform page:
  - Loading the generated `cfg/catalog.json` aggregate (the single runtime data fetch)
  - Two datasets: **IP view** (one row per IP) and **Project view** (one row per Task)
  - Search and filtering interface (results ordered alphabetically by `Name` / `Title`)
  - Card-grid rendering with pill badges for enumerated fields
  - Chip-based filter bar with per-column popovers
  - Slide-in detail drawer with a relationship tree (IP → Projects → Tasks, etc.) and an on-demand IP Card (`ip_cards/*.json|jsonc`) preview
  - CSV export functionality
  - Tab navigation between the catalogue and the compatibility matrix (the matrix is a secondary control on the top bar)
- `style.css` - Styling for the application
- `editor.html` - Companion page for editing the data files (IP documents and project documents)
- `editor.js` - JavaScript providing functionality for the editor page:
  - Loading existing `ips/<id>.json` / `projects/<id>.json` files (listed from `cfg/catalog.json`) or local upload
  - Two document kinds: an IP file is a single-record form, a project file is a spreadsheet of Tasks
  - Specialized combobox inputs for Owners/Partners (partners.json), IPs (catalogue ids), Category and License
  - Validation against the reference registries (owners, partners, IP ids, categories, licenses, task ids)
  - Saving edited data as downloadable JSON files
- `help.html` - Help documentation page

### Configuration Files
- `cfg/categories.json` - Defines IP categories and their aliases used for classification
- `cfg/projects.json` - Lists participating projects (`id`, `name`, `logo`, `url`); the `id` must match the file name under `projects/`
- `cfg/partners.json` - Organisation registry (`id`, `name`, `aliases`) backing IP `Owners` and Task `Partners` references
- `cfg/licenses.json` - Defines valid SPDX license identifiers used in the editor
- `cfg/compatibility-matrix.json` - Defines the compatibility matrix data structure (`ipName` holds an IP `Id` when the matrix cell maps to an independent IP; unmapped task labels land on the Project view)
- `cfg/repo-stats.json` - Cache of public repository statistics (stars, forks, commits, watchers, open issues, contributors, last push, detected license) for every GitHub and GitLab URL in the catalogue. Generated by `scripts/fetch_repo_stats.py`; see the "Repository Statistics" section below
- `cfg/catalog.json` - **Generated** runtime aggregate (`generated_at`, `ips`, `projects`) built by `scripts/build_catalog.py` from `ips/` + `projects/`; committed, never hand-edited
- `cfg/schema-ip.json` - JSON Schema (Draft7) for the single-IP documents under `ips/`
- `cfg/schema-project.json` - JSON Schema (Draft7) for the per-project Task documents under `projects/`
- `scripts/validate_ips.py` - Validation script enforcing both schemas plus cross-references (run: `python3 scripts/validate_ips.py`, `--strict` fails on unknown properties)
- `scripts/build_catalog.py` - Regenerates `cfg/catalog.json` (`--check` fails when the aggregate is stale or a reference is broken)
- `scripts/uap_common.py` - Shared stdlib helpers (JSON loading, partner lookup) for the scripts
- `scripts/gen_migration_map.py` / `scripts/gen_diagrams.py` / `scripts/check_diagrams.py` - Documentation generators (see "Documentation Assets")

### IP Data Files (in `/ips` directory)
One file per **independent IP**, each a single JSON object (not an array): `ips/<Id>.json` where `<Id>` is a lowercase slug matching the file name. Example dataset coverage: TRISTAN, ISOLDE, REBECCA, RIGOLETTO, Scale4Edge contributions all reference these shared IPs.

An IP document contains:
- Id: slug identifier (must match the file name)
- Name: IP/component name
- Owners: owning organizations from `cfg/partners.json` (name or alias, at least one; `"TBD"` while unassigned)
- URL: canonical repository/asset URL (empty when unknown)
- DefaultBranch: canonical branch for stats
- License: SPDX identifier(s) from licenses.json
- Status: Development status (Released, In progress, Finished, etc.)
- Category: Classification from categories.json (array or string)
- Description: Functional description
- IP_CARD_URL / IP_CARD_PDF_URL: optional IP-card links (see "IP Card Files")
- Comment: Additional notes

An IP without Tasks is legitimate — project work never lives in `ips/`.

### Project Task Files (in `/projects` directory)
One file per EU research project: `projects/<id>.json` (`tristan.json`, `isolde.json`, `rebecca.json`, `rigoletto.json`, `scale4edge.json`), each a document:
```json
{ "Id": "tristan", "Name": "TRISTAN", "Tasks": [ … ] }
```
Each Task (≡ Work Item) requires `TaskId` (unique slug, conventionally `<project>-<wi>`), `WI`, `Title`, `IPs` (one or more IP `Id`s), and `Partners` (≥1, from `cfg/partners.json`); optional `ForkURL`, `Branch`, `Status`, `Description`, `Comment`. Tasks carry **no** `Project` field — the project is the document root.

### IP Card Files (in `/ip_cards` directory)
Host IP Card assets referenced by IP entries through the `IP_CARD_URL` (JSON card, e.g. `ip_cards/FENTISS_xng.json`) and `IP_CARD_PDF_URL` (PDF card) files.
IP Cards must be hosted in `ip_cards/` - no other directory may host them (enforced by validation, see below).
The Platform page previews the `IP_CARD_URL` document inside the detail drawer (fetched lazily and cached per session; the Task drawer shows one collapsed section per card-bearing IP the task touches, loaded on expand). The card JSON has **no** committed schema (files carry `schemaVersion: "0.9"`) and **two different top-level shapes** exist in the wild, so the drawer renderer is deliberately generic. Some `.jsonc` cards contain `//` comments and LaTeX table debris left over from the PDF migration (handled by `stripJsonComments()` / `cleanCardText()` in `script.js`), and placeholder values (`null` / `"NA"` / `"-"`) are hidden rather than shown.

## How the Application Works

### Platform Page (unified-access.html)
1. **Data Loading**:
   - The runtime fetches **only** `cfg/catalog.json` (plus the `cfg/` registries and `cfg/repo-stats.json`, plus `ip_cards/*.{json,jsonc}` lazily, only when a detail drawer previews an IP Card) — never individual `ips/` files nor a repository API. GitHub Pages runs no build, so the aggregate must be committed and CI-regenerated (see "Catalogue Aggregate").
   - The local-file mode remains for previewing editor drafts: it accepts the aggregate, single IP files, or project files.
   - Two datasets are built from the aggregate: **IP rows** (one per `ips/*.json`, with a derived `Tasks` column of project · WI · title pairs) and **Task rows** (one per task in `projects/*.json`, with the project's `Name` as `Project`).

2. **User Interface Features**:
   - View selector (IPs | Projects) — a single Summary card layout; the full field set for any entry lives in the detail drawer ("Open Details" = the card title). The IPs/Projects switch is the prominent segmented control in the top bar
   - Search box for filtering across all columns (debounced)
   - Chip-based filter bar: one popover per filterable column writing into a single `filterState`, plus removable active-filter chips and "Clear all"
   - `Repo Stats` pills fed by the pre-computed `cfg/repo-stats.json` cache (see "Repository Statistics")
   - Enumerated fields (License, Owners, Partners, Project, Category, Status, WI) rendered as pills
   - Slide-in detail drawer with a re-entrant relationship tree for the selected IP/Task/Project
   - Tab switching between the catalogue and the Compatibility Matrix
   - Export to CSV functionality
   - Settings panel for data source and controls (Edit / Export CSV)

3. **Compatibility Matrix**:
   - Loaded from `cfg/compatibility-matrix.json`
   - Shows compatibility status (CT=Compatible and Tested, CNT=Compatible but Not Tested, NC=Not Compatible)
   - Clicking a cell label whose `ipName` is a real IP `Id` lands on that IP in the IP view; unmapped task labels land on the Project view filtered by the row's `project` and search the old label

4. **Accessibility Features**:
   - Screen-reader live region for status announcements
   - Native checkboxes in the filter popovers (keyboard-operable)
   - ARIA attributes for the drawer dialog and filter controls
   - Focus moves into the drawer on open and returns to the originating card on close (Escape closes the drawer; the × button and backdrop also close it)

### Editor Page (editor.html)
1. **File Operations**:
   - Pick the document kind first (IP file | Project file) — the table columns change accordingly
   - Load existing `ips/<id>.json` / `projects/<id>.json` (the file selector is populated from `cfg/catalog.json`, which works identically on GitHub Pages, GitLab Pages and self-hosting)
   - Upload local JSON files for editing (kind is auto-detected from the document shape)
   - Create new files: IP files save as `ips/<Id>.json`, project files as `projects/<Id>.json` (project picked from `cfg/projects.json`)
   - Save edited data as downloadable JSON files

2. **Data Validation** (mirrors `scripts/validate_ips.py` client-side):
   - IP file: valid `Id` slug, non-empty `Name`, ≥1 `Owner` resolvable in partners.json, ≥1 `Category`, SPDX `License`
   - Project file: valid unique `TaskId`, non-empty `WI`/`Title`, ≥1 `IP` existing in the catalogue, ≥1 `Partner` resolvable in partners.json
   - Column whitelists are rebuilt from `cfg/schema-ip.json` / `cfg/schema-project.json`, so schema additions surface in the editor automatically

3. **Editing Interface**:
   - IP kind: single-record form; Project kind: spreadsheet of Tasks with add/delete row controls
   - Specialized combobox inputs for Owners/Partners (partners.json), IPs (catalogue ids), Category and License with search-as-you-type filtering
   - Standard text inputs for other fields
   - Project selector sets the document root `Id`/`Name` of project files
   - Column resizing capabilities

4. **Data Structure**:
   - IP documents follow `cfg/schema-ip.json`, project documents `cfg/schema-project.json`
   - Array fields (Owners, IPs, Partners, WI, Category, License) are stored as arrays in JSON but displayed as comma-separated strings in the editor
   - Tasks carry no `Project` field; the project is the document root

## Development Guidelines

### Adding New IP Data (via Editor)
1. Navigate to editor.html
2. Pick the "IP file (ips/)" document kind
3. Click "Create file" (or upload/local load an existing `ips/<id>.json`)
4. Fill in the fields (single-record form):
   - Id: lowercase slug — this is also the file name (`ips/<Id>.json`)
   - Name: IP/component name
   - Owners: owners from partners.json (comma-separated; `TBD` while unassigned)
   - Category: Select from dropdown (must match categories.json)
   - URL / DefaultBranch: canonical repository URL and branch (may stay empty)
   - License: Select from dropdown (must match SPDX identifier)
   - Status: Development status (free text)
   - Description / Comment: free text
   - IP_CARD_URL / IP_CARD_PDF_URL: optional card links
5. Click "Save to JSON File" to download the file
   - Place it in the `/ips/` directory and commit via pull request

### Adding New Project Tasks (via Editor)
1. Pick the "Project file (projects/)" document kind and the project
2. Load `projects/<project>.json` (or create it)
3. Add Task rows with the "+" buttons: TaskId, WI, Title, IPs (ids from the catalogue), Partners, ForkURL, Branch, Status, Description, Comment
4. Save and place the file under `/projects/`

### Adding New IP Data (Direct JSON)
1. Create `ips/<Id>.json` — a single object following `cfg/schema-ip.json`; required: `Id` (matching the file name), `Name`, `Owners`, `Category`
2. Add a Task in the relevant `projects/<project>.json` referencing the new IP by its `Id` (required: `TaskId`, `WI`, `Title`, `IPs`, `Partners`)
3. Owner/Partner values must resolve in `cfg/partners.json` (by name or alias)
4. Category must match one defined in `cfg/categories.json` or use an alias
5. License must match an SPDX identifier from `cfg/licenses.json`
6. Regenerate the aggregate: `python3 scripts/build_catalog.py` (and commit it)
7. IP_CARD_URL / IP_CARD_PDF URL may be a full URL (http/https), an empty string, or a relative path pointing into `ip_cards/`. No other relative location is allowed, and for local paths the file extension is checked: `IP_CARD_URL` must end with `.json` or `.jsonc` (e.g. `ip_cards/FENTISS_xng.json`), `IP_CARD_PDF_URL` must end with `.pdf`. This is enforced by the `ip_card_json` / `ip_card_pdf` formats in `cfg/schema-ip.json` and validated by `scripts/validate_ips.py`

### Modifying Categories
1. Edit `cfg/categories.json` to add, remove, or modify categories
2. Each category object needs: `name` (string) and optional `aliases` (array of strings)

### Updating Projects
1. Modify `cfg/projects.json` to add or update project information
2. Each project needs: `id` (lowercase slug matching the file name under `projects/`), `name` (string) and `logo` (URL string); `url` is optional
3. Logos are displayed in the UI for filtering and in the sponsors section
4. A new project also needs a `projects/<id>.json` task document (with at least one Task) once it contributes work

### Updating Licenses
1. Edit `cfg/licenses.json` to add, remove, or modify license options for the editor
2. Each license object needs: `licenseId` (SPDX identifier) and `name` (human-readable name)
3. The editor validates License fields against the licenseId values

### Styling Changes
1. Edit `style.css` for visual modifications affecting both pages
2. The application uses CSS variables and responsive design principles
3. Pay attention to the matrix-specific styles for compatibility view
4. Editor-specific styles include table layout, combobox styling, and action buttons

### JavaScript Modifications
#### Platform Page (script.js)
1. Core logic is in `script.js`
2. The platform page renders as a **card grid** (not an HTML table) with a chip filter bar and a slide-in detail drawer. `editor.html` still uses the table markup and CSS; do not remove the `#data-table` styles.
3. Key functions to understand:
   - `loadCatalog()` / `applyCatalog()` - fetch the single `cfg/catalog.json` and build the two datasets (IP rows, Task rows), then build the relationship indices
   - `buildRelationIndices()` - inverts Task.IPs[]/project containment into `ipById`, `indexTasksByProject`, `indexTasksByIp` for the drawer tree
   - `rebuildActiveDataset()` / `onViewChanged()` - swap datasets + re-derive columns when the view changes (filterState is retained, not reset)
   - `renderCards()` / `renderCardValue()` - render filtered rows as `.entity-card` elements (pills, repo stats, IP-card links, task list)
   - `applyFilters()` - filtering driven by `filterState` (single source of truth: `{ column: [values] }`); filters on columns not in the active view are retained but not applied
   - `buildFilterBar()` / popover + `renderActiveChips()` - one popover per filterable column writing directly into `filterState`; removable chips + "Clear all"
   - `openDetailDrawer(type, row|projectName)` / `ipTree()` / `taskTree()` / `projectTree()` - right-side drawer with a re-entrant relationship tree
   - `setView()` / `setupViewSwitcher()` - the top-bar IPs/Projects segmented control
   - `loadIpCard()` / `mountIpCardPreview()` / `renderCardValueNode()` / `httpUrl()` - lazy, cached, token-guarded IP Card (`ip_cards/*.{json,jsonc}`) preview in the detail drawer. `isValidUrl` must stay http(s)-only (it guards many data-driven hrefs); `httpUrl()` layers scheme-less-host promotion on top of it for URLs found *inside* card JSON
   - Tab handling (`switchTab`/`switchToCatalogue`) - the Compatibility Matrix is now a secondary control; both directions still work
   - `parseRepoRefs()` - must stay in sync with `scripts/fetch_repo_stats.py`

#### Editor Page (editor.js)
1. Core logic is in `editor.js`
2. Key functions to understand:
   - `initialize()` - loads configuration data (categories, licenses, partners, projects, catalogue, schemas)
   - `fieldsForKind()` - builds the column whitelist from the two schemas
   - `loadFileData()` / `detectKind()` - fetch and parse an IP or project document
   - `createNewFile()` - initializes editor for a new IP or project document
   - `renderTable()` / `makeCombobox()` - builds the editable table with registry-backed comboboxes
   - `updateData()` - modifies the internal data model from UI changes
   - `validate()` / `saveFile()` - reference validation and downloadable JSON
   - Row insertion/deletion functionality

### Browser Compatibility
- Uses modern JavaScript features (fetch, arrow functions, etc.)
- Tested with recent versions of major browsers
- No transpilation or build process required - pure static HTML/CSS/JS

## Repository Statistics

The Platform page shows a Repo Stats column with public repository statistics for every IP whose URL points to GitHub or to a project on any GitLab instance (gitlab.com or self-hosted, detected by the hostname containing `gitlab`). The data is pre-computed offline, so anonymous visitors never contact the GitHub or GitLab APIs (unauthenticated GitHub calls are limited to 60 requests/hour per IP, far below the ~100 repository URLs in the catalogue).

- `cfg/repo-stats.json` is the cache consumed by `script.js`. Contract:
  - `generated_at` (ISO timestamp) and `source` at the top level
  - `repos`: map of lowercase `"<host>/owner/repo"` keys (e.g. `github.com/pulp-platform/cva6`, `gitlab.com/selene-riscv-platform/euros2pronoc`) to a record with `repo`, `provider` (`github`/`gitlab`), `host`, `html_url`, `stars`, `forks`, `watchers`, `open_issues`, `commits`, `contributors`, `language`, `license_spdx_id`, `default_branch`, `pushed_at`, `archived`, `fetched_at`, `etag`. GitLab records have `watchers: null` (not exposed by the public API, rendered as `n/a`), `language: null`, and `pushed_at` from `last_activity_at`; their `open_issues` combines opened issues + merge requests and `commits` is counted by paging (best effort, capped)
  - `errors`: map of key to the failure reason (deleted/private/renamed repos)
- Regenerate manually: `python3 scripts/fetch_repo_stats.py` (stdlib only; options `--dry-run`, `--only-missing`, `--max-age-hours`, `--limit-repos`, `--ips-dir`, `--projects-dir`, `--out`, `--auth-token`, `--gitlab-token`). It scans **both** `ips/*.json` (canonical `URL` / `DefaultBranch`) and `projects/*.json` (`ForkURL` / `Branch`), so task fork repositories are covered too. Set the `GITHUB_TOKEN` environment variable to raise the GitHub rate limit, and optionally `GITLAB_TOKEN` for GitLab (sent as `PRIVATE-TOKEN` to GitLab hosts only).
- Automation: `.github/workflows/repo-stats.yml` runs weekly (and on `workflow_dispatch`) and commits the refreshed cache with `[skip ci]`; the GitLab mirror is the `repo_stats` job in `.gitlab-ci.yml`.
- Stats are not stored in `ips/*.json`: `editor.js` rebuilds documents from a schema-derived field whitelist (silently dropping unknown fields) and `scripts/validate_ips.py --strict` rejects properties absent from the schemas. The separate cache file avoids both problems.
- The URL to `<host>/owner/repo` normalisation lives twice and must stay in sync: `GithubProvider.parse_repos()` / `GitlabProvider.parse_repos()` in `scripts/fetch_repo_stats.py` and `parseRepoRefs()` in `script.js`. GitLab nested subgroups (`group/sub/project`) are a known limitation in both parsers.

## Catalogue Aggregate

The site loads `cfg/catalog.json` — a **generated** aggregate of every `ips/*.json` and `projects/*.json` document (shape: `{ generated_at, source, ips: { <id>: … }, projects: { <id>: … } }`).

- Source of truth stays per-file (`ips/`, `projects/`); the aggregate is a committed build artifact, never hand-edited.
- Regenerate after any data change: `python3 scripts/build_catalog.py` (deterministic output — a `git diff` appears only when data actually changed; `generated_at` is preserved when the payload is unchanged). It also performs all referential checks, so one command verifies and rebuilds.
- `--check` mode (used by CI on every PR) fails when the aggregate is missing, stale, or a reference is broken.
- Automation: `.github/workflows/build-catalog.yml` (weekly + `workflow_dispatch`) and the `build_catalog` job in `.gitlab-ci.yml` regenerate and commit it with `[skip ci]`. GitHub Pages runs **no build**, so the committed file is what visitors get — a data change merged without a regenerated aggregate shows on the site only after the next CI run; pushing a regenerated aggregate with the data in the same PR avoids that gap.
- The runtime never fetches individual `ips/`/`projects/` files or a repository API; transport-level gzip/brotli covers the ~250-300 KB aggregate.

## GitHub Integration

The application is hosting-agnostic: it works on GitHub Pages, GitLab Pages, and any static host:
- Platform page: the single data request is `cfg/catalog.json` (plus `cfg/` registries and `cfg/repo-stats.json`), all same-origin relative fetches
- The editor's file selector is also driven by `cfg/catalog.json` (ids → individual committed files), so it behaves identically everywhere without directory listings or repository APIs
- Saved files should be placed in `/ips/` or `/projects/` and committed via pull request

## Documentation Assets

- `docs/migration-map.md` — entry-by-entry record of the IP-centric migration plus the human review checklists (owners `TBD`, `PROVISIONAL` markers, compatibility-matrix remapping). Regenerate with `python3 scripts/gen_migration_map.py` (reads `cfg/catalog.json` + the remapping tables in `scripts/gen_migration_map.py`).
- `docs/diagrams/UAP-Domain-Model.drawio.svg`, `UAP-Architecture.drawio.svg`, `UAP-Contribution-Workflow.drawio.svg` — valid, editable draw.io SVGs generated by `scripts/gen_diagrams.py`; do not hand-edit the SVG files, edit the specs in the script and regenerate (`python3 scripts/check_diagrams.py` verifies well-formedness).

As a static site, this can be deployed to:

## Maintenance Notes

1. The application handles data loading errors gracefully with status updates
2. Loading state is managed through the status element and screen-reader announcements
3. Filter state can be preserved via URL parameters (`?filter_Column=value1,value2`); a link targeting the other view's columns (e.g. `?filter_Project=TRISTAN`) switches the view automatically
4. Cross-document communication supported via postMessage for filter setting
5. Local storage is not used - all state is in memory and URL-based
6. Editor validates slugs, uniqueness, owners/partners/IP references, categories and licenses before saving
7. Array fields are properly handled as both JSON arrays and comma-separated strings for editing
8. After editing any `ips/` or `projects/` data, run `python3 scripts/validate_ips.py --strict` and `python3 scripts/build_catalog.py` before committing
9. Cards are ordered alphabetically by `Name` / `Title` (a deterministic `Intl.Collator` sort in `applyFilters()`); there is no completeness ranking
10. All four pages (`index`, `unified-access`, `editor`, `help`) declare `images/logo_unified-riscv.png` as their favicon with a **relative** URL — Pages hosting uses a sub-path, so a root-absolute `/favicon.ico` would break; there is deliberately no crop script, no Pillow dependency and no `.ico` asset
