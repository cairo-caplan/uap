# OpenHW Unified RISC-V Access Platform (UAP) - Agent Guide

## Project Overview

This repository hosts the Unified RISC-V Access Platform (UAP), a static website that serves as a catalog and access point for RISC-V IP assets developed in European research projects such as TRISTAN and ISOLDE. The platform provides:

- IP catalogue with search and filtering capabilities
- Compatibility matrix showing interoperability between components
- Documentation and status information for hardware and software components
- Links to source repositories hosted on OpenHW Foundation GitHub or on 3rd parties website or repositories
- Editor functionality for creating and modifying IP data files

## Key Directories and Files

### Core Application Files
- `unified-access.html` - Main HTML page implementing the IP catalogue and compatibility matrix. Also called the Platform page.
- `script.js` - JavaScript application providing dynamic functionality for the Platform page:
  - Loading IP data from JSON files (local or GitHub)
  - Search and filtering interface
  - Table rendering with column sorting and resizing
  - Dropdown filters for each column
  - CSV export functionality
  - Tab navigation between catalogue and compatibility matrix views
- `style.css` - Styling for the application
- `editor.html` - Companion page for editing table data (JSON files)
- `editor.js` - JavaScript providing functionality for the editor page:
  - Loading existing JSON files from GitHub or local upload
  - Creating new IP entries with validation
  - Table-based editing with row insertion/deletion
  - Specialized combobox inputs for Category and License fields
  - Saving edited data as downloadable JSON files
- `help.html` - Help documentation page

### Configuration Files
- `cfg/categories.json` - Defines IP categories and their aliases used for classification
- `cfg/projects.json` - Lists participating projects with their logos for display
- `cfg/licenses.json` - Defines valid SPDX license identifiers used in the editor
- `cfg/compatibility-matrix.json` - Defines the compatibility matrix data structure
- `cfg/repo-stats.json` - Cache of public repository statistics (stars, forks, commits, watchers, open issues, contributors, last push, detected license) for every GitHub and GitLab URL in the catalogue. Generated by `scripts/fetch_repo_stats.py`; see the "Repository Statistics" section below
- `cfg/schema.json` - JSON Schema (Draft7) that all `ips/*.json` files must validate against
- `scripts/validate_ips.py` - Validation script enforcing `cfg/schema.json` (run: `python3 scripts/validate_ips.py`, `--strict` fails on unknown properties)

### IP Data Files (in `/ips` directory)
JSON files containing IP information for each project:
- `tristan.json` - TRISTAN project IP assets
- `isolde.json` - ISOLDE project IP assets
- `rebecca.json` - REBECCA project IP assets
- `scale4edge.json` - Scale4Edge project IP assets

### IP Card Files (in `/ip_cards` directory)
Host IP Card assets referenced by IP entries through the `IP_CARD_URL` (JSON card, e.g. `ip_cards/FENTISS_xng.json`) and `IP_CARD_PDF_URL` (PDF card) fields.
IP Cards **must** be hosted in `ip_cards/` - no other directory may host them (enforced by validation, see below).

Each IP entry includes fields like:
- Name: IP/component name
- URL: Link to source repository
- License: Licensing information (must match SPDX identifiers from licenses.json)
- Status: Development status (Released, In progress, Finished, etc.)
- Description: Functional description
- Project: Associated project name
- WI: Work item identifiers (can be array or comma-separated string)
- Partners: Involved organizations (can be array or comma-separated string)
- Comment: Additional notes
- Category: Classification from categories.json

## How the Application Works

### Platform Page (unified-access.html)
1. **Data Loading**:
   - By default loads data from GitHub by fetching JSON files from the `/ips/` directory
   - Can also load from local files via file input
   - Processes each IP entry, adding Category field based on filename patterns
   - Handles both direct JSON arrays and GitHub API response formats

2. **User Interface Features**:
   - Search box for filtering across all columns
   - Column-specific dropdown filters with checkboxes
   - `Repo Stats` column fed by the pre-computed `cfg/repo-stats.json` cache (see "Repository Statistics")
   - Resizable columns via drag handles
   - Tab switching between IP Catalogue and Compatibility Matrix views
   - Export to CSV functionality
   - Settings panel for data source selection and view mode

3. **Compatibility Matrix**:
   - Loaded from `cfg/compatibility-matrix.json`
   - Shows compatibility status (CT=Compatible and Tested, CNT=Compatible but Not Tested, NC=Not Compatible)
   - Clicking on column headers or row labels navigates to filtered catalogue view

4. **Accessibility Features**:
   - Screen-reader live region for status announcements
   - Keyboard navigation for dropdowns (Enter/Space to open, Arrow keys for navigation)
   - ARIA attributes for dropdown buttons and menus
   - Focus management for modal dialogs

### Editor Page (editor.html)
1. **File Operations**:
   - Load existing JSON files from GitHub repository (`/ips/` directory)
   - Upload local JSON files for editing
   - Create new JSON files from scratch
   - Save edited data as downloadable JSON files

2. **Data Validation**:
   - Ensures "Name" field is not empty and contains unique values
   - Validates License field against allowed SPDX identifiers from licenses.json
   - Automatically formats array fields (WI, Partners, Category, License) as comma-separated strings

3. **Editing Interface**:
   - Spreadsheet-like table with add/delete row controls
   - Specialized combobox inputs for Category and License fields with search-as-you-type filtering
   - Standard text inputs for other fields
   - Project name field that applies to all entries in the file
   - Column resizing capabilities

4. **Data Structure**:
   - Follows schema: Name, URL, License, Status, Description, Project, WI, Partners, Comment, Category
   - Array fields (WI, Partners, Category, License) are stored as arrays in JSON but displayed as comma-separated strings in the editor
   - Project name is added to each entry during save

## Development Guidelines

### Adding New IP Data (via Editor)
1. Navigate to editor.html
2. Click "Create file" or upload/local load an existing file
3. Enter a Project Name (required for saving)
4. Add rows as needed using the "+" buttons in each row
5. Fill in the fields:
   - Name: IP/component name (must be unique and non-empty)
   - URL: Link to source repository
   - License: Select from dropdown (must match SPDX identifier)
   - Status: Development status (free text)
   - Description: Functional description
   - WI: Work item identifiers (comma-separated)
   - Partners: Involved organizations (comma-separated)
   - Comment: Additional notes
   - Category: Select from dropdown (must match categories.json)
6. Click "Save to JSON File" to download the file
   - The file will be named `[Project Name].json`
   - Place it in the `/ips/` directory to make it available in the platform

### Adding New IP Data (Direct JSON)
1. Create a new JSON file in the `/ips/` directory following naming convention: `[project].json`
2. Each file should contain an array of IP objects with at minimum: Name, URL, License, Status, Description, Project, Category
3. Optional fields: WI (array or string), Partners (array or string), Comment
4. Category must match one defined in `cfg/categories.json` or use an alias
5. License must match an SPDX identifier from `cfg/licenses.json`
6. IP_CARD_URL / IP_CARD_PDF_URL may be a full URL (http/https), an empty string, or a **relative path pointing into `ip_cards/`**. No other relative location is allowed, and for local paths the file extension is checked: `IP_CARD_URL` must end with `.json` or `.jsonc` (e.g. `ip_cards/FENTISS_xng.json`), `IP_CARD_PDF_URL` must end with `.pdf`. This is enforced by the `ip_card_json` / `ip_card_pdf` formats in `cfg/schema.json` and validated by `scripts/validate_ips.py`

### Modifying Categories
1. Edit `cfg/categories.json` to add, remove, or modify categories
2. Each category object needs: `name` (string) and optional `aliases` (array of strings)
3. The application automatically derives Category from filenames when loading local files in unified-access.html:
   - Files must have at least 2 dots: `prefix.category.suffix.json`
   - The middle part is matched against category names and aliases

### Updating Projects
1. Modify `cfg/projects.json` to add or update project information
2. Each project needs: `name` (string) and `logo` (URL string)
3. Logos are displayed in the UI for filtering and in the sponsors section

### Updating Licenses
1. Edit `cfg/licenses.json` to add, remove, or modify license options for the editor
2. Each license object needs: `licenseId` (SPDX identifier) and `name` (human-readable name)
3. The editor validates License fields against the licenseId values

### Styling Changes
1. Edit `style.css` for visual modifications affecting both pages
2. The application uses CSS variables and responsive design principles
3. Pay attention to the matrix-specific styles for compatibility view
4. Editor-specific styles include table layout, combobox styling, and action buttons

### JavaScript Modifications
#### Platform Page (script.js)
1. Core logic is in `script.js`
2. Key functions to understand:
   - `loadDataFromServer()` - fetches and processes IP data from remote sources
   - `buildTable()` - constructs the HTML table with filters
   - `applyFilters()` - implements filtering logic (OR logic within columns, AND between columns)
   - `renderRows()` - creates table rows with proper formatting
   - Dropdown filter implementation - complex system for column-based filtering
   - Column resizing - allows users to adjust column widths
   - Tab handling - switches between catalogue and matrix views

#### Editor Page (editor.js)
1. Core logic is in `editor.js`
2. Key functions to understand:
   - `initialize()` - loads configuration data (categories, licenses, file list)
   - `loadFileData()` - fetches and parses JSON file data
   - `createNewFile()` - initializes editor for new file creation
   - `renderTable()` - builds the editable table with specialized inputs
   - `updateData()` - modifies the internal data model from UI changes
   - `saveFile()` - validates data and generates downloadable JSON
   - Specialized combobox handling for Category and License fields
   - Row insertion/deletion functionality
   - Data validation (unique names, valid licenses)

### Browser Compatibility
- Uses modern JavaScript features (fetch, arrow functions, etc.)
- Tested with recent versions of major browsers
- No transpilation or build process required - pure static HTML/CSS/JS

## Repository Statistics

The Platform page shows a **Repo Stats** column with public repository statistics for every IP whose `URL` points to GitHub or to a project on any GitLab instance (gitlab.com or self-hosted, detected by the hostname containing `gitlab`). The data is **pre-computed offline**, so anonymous visitors never contact the GitHub or GitLab APIs (unauthenticated GitHub calls are limited to 60 requests/hour per IP, far below the ~100 repository URLs in the catalogue).

- `cfg/repo-stats.json` is the cache consumed by `script.js`. Contract:
  - `generated_at` (ISO timestamp) and `source` at the top level
  - `repos`: map of **lowercase** `"<host>/owner/repo"` keys (e.g. `github.com/pulp-platform/cva6`, `gitlab.com/selene-riscv-platform/euros2pronoc`) to a record with `repo`, `provider` (`github`/`gitlab`), `host`, `html_url`, `stars`, `forks`, `watchers`, `open_issues`, `commits`, `contributors`, `language`, `license_spdx_id`, `default_branch`, `pushed_at`, `archived`, `fetched_at`, `etag`. GitLab records have `watchers: null` (not exposed by the public API, rendered as `n/a`), `language: null`, and `pushed_at` from `last_activity_at`; their `open_issues` combines opened issues + merge requests and `commits` is counted by paging (best effort, capped)
  - `errors`: map of key to the failure reason (deleted/private/renamed repos)
- Regenerate manually: `python3 scripts/fetch_repo_stats.py` (stdlib only; options `--dry-run`, `--only-missing`, `--max-age-hours`, `--limit-repos`, `--ips-dir`, `--out`, `--auth-token`, `--gitlab-token`). Set the `GITHUB_TOKEN` environment variable to raise the GitHub rate limit, and optionally `GITLAB_TOKEN` for GitLab (sent as `PRIVATE-TOKEN` to GitLab hosts only).
- Automation: `.github/workflows/repo-stats.yml` runs weekly (and on `workflow_dispatch`) and commits the refreshed cache with `[skip ci]`.
- Stats are **not** stored in `ips/*.json`: `editor.js` rebuilds rows from a field whitelist (silently dropping unknown fields) and `scripts/validate_ips.py --strict` rejects properties absent from `cfg/schema.json`. The separate cache file avoids both problems.
- The URL → `<host>/owner/repo` normalisation lives twice and must stay in sync: `GithubProvider.parse_repos()` / `GitlabProvider.parse_repos()` in `scripts/fetch_repo_stats.py` and `parseRepoRefs()` in `script.js`. GitLab nested subgroups (`group/sub/project`) are a known limitation in both parsers.

## GitHub Integration

The application is hosting-agnostic: it works on GitHub Pages, GitLab Pages, and any static host:
- Base URL is derived from `window.location.href`
- Platform page attempts to load IP data from `<base_url>/ips/` directory
- Falls back to the GitHub or GitLab repository API only when derivable from the current location (never a hardcoded third-party repository)
- Can construct raw file URLs (raw.githubusercontent.com or GitLab `/-/raw/`) for fallback loading
- Editor page derives its ips/ file list from the same-origin directory listing first, then GitHub/GitLab APIs derived from the current location
- Saved files should be placed in the `/ips/` directory and committed via pull request

## Deployment

As a static site, this can be deployed to:
- GitHub Pages (primary intended platform)
- Any static web hosting service
- No server-side processing required

## Maintenance Notes

1. The application handles data loading errors gracefully with status updates
2. Loading state is managed through the status element and screen-reader announcements
3. Filter state can be preserved via URL parameters (`?filter_Column=value1,value2`)
4. Cross-document communication supported via postMessage for filter setting
5. Local storage is not used - all state is in memory and URL-based
6. Editor includes validation to prevent empty names and duplicate names
7. Editor validates licenses against allowed SPDX identifiers
8. Array fields are properly handled as both JSON arrays and comma-separated strings for editing
